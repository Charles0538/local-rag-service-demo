## 本地知识库问答（RAG）· 已跑通

> 主题选「家电售后」的原因：这是我在京东服务做过的域（售后履约、工程师上门、工单投诉），语料是虚构脱敏的，讲起来不用背、也不怕被追问细节。

**一句话**：把 6 份售后知识库文档（32 个知识块）变成能问答的助手，全部在本机跑，数据不出机器。

### 三层结构（面试就讲这三层）

```
用户问题
   ↓
① 护栏层   7 条红线规则，命中直接固定话术拒答（不检索、不调模型）
   ↓
② 检索层   bge-m3 把问题变成向量 → 和 32 个知识块算余弦相似度 → 取 top5（同文档最多 2 块）
   ↓  最高分 < 0.45 视为「知识库里没有依据」→ 直接拒答，不硬答
      （0.45 是实测校准值：相关问题分布 0.72-0.77，无关问题 0.36-0.38，门槛取两类之间）
③ 生成层   qwen2.5:7b，把 top5 拼进 prompt，强制只依据资料回答 + 标引用编号 [n]
   ↓
回答 + 溯源（本条答案依据了哪几份文档）
```

### 实测数字（2026-11-22，本机）

| 项 | 数值 |
|---|---|
| 知识库规模 | 6 份文档 / 32 个知识块 / 单块 ≤ 700 字 |
| 索引构建 | 2.34 s（一次性；存 `.rag_index.json`，之后秒开） |
| 检索耗时 | 42–86 ms（热）；7 s（首次，bge-m3 冷加载） |
| 生成速度 | 15.2–16.1 token/s |
| 单次问答端到端 | 5–15 s（看回答长度） |
| 向量模型 | bge-m3（1.2 GB，1024 维） |

### 六个实测发现（这部分比代码值钱）

1. **检索分高 ≠ 有依据。** 问「冰箱保修十年是真的吗」，最高分 0.68（因为语义相关），但知识库里根本没有这条——靠 prompt 里「无依据必须说不收录」兜住。**分数只说明"像"，不说明"有"。**
2. **7B 对否定式规则执行力很弱。** 我写了「涉及他人隐私一律拒绝」「不做竞品比价」，实测模型会顺着资料答价格表、把隐私问题转给人工。**改法：红线不交给模型判断，用代码在检索前拦截。** 这也印证了企业里「规则引擎 + LLM」分层的必要性。
3. **改 prompt 能救回漏答，但要看问题在哪一层。** 「师傅爽约怎么投诉」一开始只答投诉渠道、漏掉赔付标准；检索命中的块里明明有赔付条款——说明**问题在生成层不在检索层**。把 prompt 规则从 3 条加到 7 条（明确"问怎么办时必须给处理结果与补偿标准"）后，答案补全。
4. **同一份文档会挤占 top-k。** 问了几个问题后发现 top5 里 4 块来自同一个文件，答案视角单一。加 `MAX_PER_FILE=2` 后来源分布正常。
5. **邻位污染（最险的一个）。** 做坏实验删掉「冰箱整机保修 1 年」后问「冰箱保修多久」——它没有拒答，而是答了「整机 3 年、电机 3 年」：把同一块里**洗衣机**的条款安到了冰箱头上。修好邻位污染后它又改拿常识填空（编了个"一年"）。**修法 = 混合检索：向量管"像不像"，关键词管"是不是"，问题含品类词时，召回块必须同时命中品类词和主题词，全被滤光就触发拒答。** 这就是企业里 hybrid search 的真实动机——不是为了快，是为了防"像但不是"。
6. **prompt 规则的执行是概率性的。** 同一条"资料里有赔付条款必须写出"的规则，7B 有时执行、有时无视，重跑两次结果不同。**结论：关键内容不能指望 prompt 兜底——要么上更强模型，要么在代码层做结构化抽取，要么靠评测集盯住这个 case。** 这也是为什么评测必须是日常机制而不是一次性动作。

### 已知局限（面试主动说，别等被问）

- 切块只按标题切，不识别语义边界；表格和跨小节的引用会断
- 没有 rerank，top5 里仍有噪声块
- 关键词护栏是窄规则，覆盖不了改写过的问法
- 7B 在 5 块约 3000 字上下文时已有注意力衰减，会漏条款
- 单轮问答，无会话记忆、无工具调用

## 评测基线（Day2 · 2026-11-23）

> 没有评测，改 prompt、换模型、调参数都是赌博。这一节就是那把尺子。

### 方法：关键事实锚点法（二值法）

每题预置 1–3 组「锚点」，锚点全部来自知识库**原文硬事实**（金额 / 时限 / 年限 / 关键动作），
每组命中其一即可，全部命中 = PASS。不用 LLM 打分——基线必须**可复现、零成本、可解释**。

同时记录每题走了哪一层（**护栏 / 拒答 / 生成**）：红线题要求"该走护栏的必须走护栏"，
这是成本（护栏 0 秒 vs 生成 5-10 秒）与安全的双重验收。

### 基线结果（qwen2.5:7b + bge-m3，MIN_SCORE=0.45）

**单次全量：通过 9/10 ｜ 护栏拦截 2/2 ｜ 生成层均耗 7.1s**

| 分组 | 结果 | 说明 |
|---|---|---|
| 对抗 / 红线 | 护栏 2 条全拦（隐私/比价，0.0s，未调模型） | 虚假信息纠正题（"冰箱保修十年"）正确用真实条款反驳 |
| 常见问题 | 4/5 | 唯一失败见下 |
| 长尾 | 爽约题**单次通过但不稳定**，连跑 5 次通过 3/5 | 见下 |

### 两个比分数更有价值的发现

1. **Q001（保修期内上门费）：答案"过于绝对"。** 它答「保修期内上门维修不收费」——单看不算错，
   但知识库原文还有「人为损坏收 50 元检测费」的例外条款被它省略了。生产环境里这就是客诉：
   用户被收了 50 元，而客服机器人之前告诉他"不收费"。**评测集抓的就是这种"单次对话没错、业务上会翻车"的 case。**
2. **爽约题通过率 3/5：把「prompt 执行概率性」从体感变成了数字。** 同一个问题、同一套系统，
   赔付标准（50 元服务券）有时写出有时漏——这就是第 6 条实测发现的量化版。
   结论不变：**关键内容不能指望 prompt 兜底**，正解是结构化抽取（金额由代码保证、模型只组织语言）。

### 评测集自身的治理点（原型阶段就暴露了）

- Q001 在模板里标了「红线」，Q009（比价）却没标——红线口径（"金额/权益类必须准确"）
  本身需要定义清楚，否则分数不可信
- 10 条里 6 条是常见问题，对抗样本占比 30%——真实生产评测集对抗样本应该占 1/3 以上且持续补充
- 单次跑分 ≠ 稳定性：重要 case 要固定题多次跑（或固定 seed），报"通过率"而不是"通没通过"

## 为什么装 7B 而不是 14B（2026-11-10 说明）

已装的是 **qwen2.5:7b**（7B 参数、Q4 量化、4.7GB），确认无误。

**没装 14B 的三条理由：**

1. **内存账**：14B 的 Q4 量化约 9GB。你这台 24GB 统一内存要同时养系统、浏览器、编辑器——跑 14B 会把内存压到接近上限，一旦触发换页，速度会掉到 8–10 token/s，反而更慢，且机器发烫、风扇响
2. **目标不同**：这一阶段的目标是「跑通 + 测数 + 祛魅」，不是追求效果上限。7B 足够让你体会部署、调用、测速、算成本的全链路
3. **迭代速度**：接下来做 RAG demo 要反复调用模型几十次，7B 每次快一倍，调试体验完全不同

**14B 的正确用法（可选实验，不做也不影响）：**

装一个 14B，用同一个问题跑两次，记录「速度 × 质量」的差异——这本身就是面试素材：

```bash
ollama pull qwen2.5:14b      # 约 9GB，视网速 1–2 小时，可睡前挂着
python3 01_call_model.py "同一个问题"   # 改脚本里 MODEL 为 qwen2.5:14b
```

然后你能说一句很有分量的话：**「我对比过 7B 和 14B：质量差别在长回答里才明显，但速度掉一半、内存吃两倍——这就是为什么很多企业场景最终选小模型加 RAG，而不是堆大模型。」**
